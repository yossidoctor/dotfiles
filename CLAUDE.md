# dotfiles CLAUDE.md

## This repo

Personal dotfiles managed via [dotbot](https://github.com/anishathalye/dotbot). `install.conf.yaml` declares every symlink + shell command; `./install` is idempotent. Symlink-edit rules live in the global `~/.claude/CLAUDE.md` ("Workspace mechanics") — not repeated here.

**Rule scope.** This file covers `~/dotfiles` only. Cross-project behavioral rules live in `~/.claude/CLAUDE.md` (always loaded). A project's rules live in that project's own `CLAUDE.md` and load only when its directory is the session root — they don't apply here, and rules here don't apply there.

**This repo is public.** It names no private layer and nothing from the employer's world; `git/hooks/pre-commit` blocks a commit whose staged tree does. A layer that needs something from here reaches it through a deployed path (`~/.claude/…`, `~/.config/git/…`), never through this repo's tree, and this repo never names the layer.

**Commit straight to `master` — no branches, no PRs.** Solo personal repo, so a PR has no reviewer and a branch adds nothing. Push to `master` directly. (Overrides any default "branch before committing on the default branch" habit — that's for shared repos, not this one.) This rule is the enforcement — no hook backs it. Falsifier: a `git branch`/`checkout -b`/`switch -c`, a push to any ref other than `master`, or a `gh pr create` targeting `~/dotfiles` -> rule broken; delete the branch/PR and land the commit on `master`.

Read README.md first. Owns layout, hooks, defaults. This CLAUDE.md only covers the editing rules and fragile bits that aren't obvious from reading the code.

## Adding a new dotfile

See README's "Adding new dotfiles" — copy into topic dir, declare in `install.conf.yaml`, run `./install`, commit the topic file + yaml together.

## Fragile bits

- **Brewfile sections.** Grouped by function under `# ── <group> ──` headers (read the file for the current groups); all `tap` lines live in the top `taps` block. Add a new entry under the group it fits, alphabetically by name within the group regardless of `brew`/`cask` kind.
- **Permission arrays are hand-edited.** `claude/global/settings.json` holds the rules that apply everywhere; Claude Code merges permission rules across settings scopes (union), so a project layer's settings file adds only its extras and never re-lists a global entry. `deny`/`ask` are safety-critical — review every change individually; don't bulk-add — propose first, get approval.
- **A new hook touches four places.** Script in `claude/global/hooks/`; registration in `claude/global/settings.json`; a **per-file** link line in `install.conf.yaml`; a row in README's hook table. Regex-gating hooks also get a `cases-<hook>.txt` in `tests/`. What it's not: banner/nudge hooks with no allow/deny logic need no case file. Falsifier: a tracked hook script missing its settings.json registration, a hook with no install.conf.yaml line, or a registered hook absent from the README hook table.
- **Hook regexes are tested.** `claude/global/hooks/tests/run-tests.sh` runs table-driven allow/deny cases against the hooks (one `cases-<hook>.txt` per covered hook — the case-file glob in that dir is the coverage list); a project layer's runner execs the same harness at its deployed path, `~/.claude/hooks/tests/run-tests.sh`. Run the runner after any hook regex change; add a case per new pattern. Edits are live instantly — the deployed hook paths are symlinks into this repo, so the next tool call in the editing session runs the changed script (`settings.json` hook registrations snapshot at session start; script bodies don't), and a broken edit bricks that tool immediately. Note: the case files contain the banned patterns as text, so write them with the Write/Edit tools — a Bash heredoc gets denied by the hook itself.
- **README hook tables and § Statusline are mirrors of code.** A behavior change to a hook or to `statusline-command.sh` updates the matching README row/section in the same commit — nothing nudges this. Falsifier: a commit changes a hook's user-visible behavior or the statusline render with no README diff.
- **install.conf.yaml is source of truth.** A file not declared there isn't deployed. Edits to a tracked file that lives outside the declared structure are invisible to dotbot.

## Script conventions

*When writing or editing any shell script in this repo.*

- **Script header comments are doc-SoT — keep and maintain them.** README § Claude Code hooks declares each script's header comment the SoT for its behavior and rationale; the convention holds beyond hooks (`mac/`, `git/`, `aerospace/` scripts carry them), and `_comment_*` keys in JSON configs serve the same role. Where a README section documents a script instead (e.g. § Statusline for `statusline-command.sh`), that section is the SoT and the script stays headerless. The header block is documentation — the global `§ No comments` rule does not apply to it; update it when behavior changes. What it's not: license for body comments — below the header, the global rule still holds. Falsifier: a diff deletes or thins a header block / `_comment_*` key, ships a new script without a header, or leaves a header asserting behavior the script no longer has.
- **Stay bash-3.2-compatible.** macOS ships bash 3.2 as `/bin/bash`; install-run scripts and git/Claude hooks may execute under it. Avoid bash-4+ syntax — `${var,,}`/`${var^^}` case-expansion, `declare -A` associative arrays, `printf '%(...)T'` — use `tr`, a parallel-array idiom, or `date` instead; version-gate (`((BASH_VERSINFO[0]>=4))`) only if you need 4+. What it's not: scripts that opt into Homebrew bash 5 via the env-shebang below *and* never run under a hook/`./install` path may use 4+ features. Falsifier: a tracked script uses `${var,,}`, `declare -A`, or `printf %()T` with no version gate.
- **`#!/usr/bin/env bash`, not `#!/bin/bash`.** Env-form resolves Homebrew bash 5 from PATH where available, falling back to system bash; a hardcoded `/bin/bash` pins you to 3.2 unconditionally. What it's not: `#!/bin/sh` where POSIX-only is intended (e.g. `git/credential-helper.sh`). Falsifier: a tracked `*.sh` starts `#!/bin/bash` -> switch to `#!/usr/bin/env bash`.
- **Install-run scripts must be idempotent; gate noisy/expensive ops behind a stamp or state check.** Re-running `./install` reruns every `shell:` action, so a script that registers login items, imports prefs, or kills/relaunches apps must no-op when the intended state already holds (check current state, or track intent in a stamp file) rather than re-doing the side effect each run. What it's not: cheap pure `defaults write`s that are already idempotent by nature. Falsifier: a new `install.conf.yaml` `shell:` script re-applies a visible side effect (relaunch, registration, import) on a second `./install` with no guard.
- **sudo / interactive `shell:` steps get `|| true`.** A non-interactive `./install` runs under `set -e`; a step needing a TTY for sudo (e.g. `mac/disable-spotlight.sh`) fails its prompt and would abort the whole run. Suffix the `install.conf.yaml` command with `|| true` so it skips cleanly, and make the script re-runnable manually with a TTY. Falsifier: an `install.conf.yaml` `shell:` entry invokes sudo or an interactive prompt without a trailing `|| true`.
